# Прошивка — вимоги

Що прошивка ESP32 має робити, у якому порядку і з якими порогами. Піни — connections.md, DPS — dps5015-modbus.md, вимірювання — measurement.md, протокол — protocol.md. Середовище: PlatformIO, Arduino-ESP32 (ESP-IDF під капотом); бібліотеки: `ModbusMaster`, `Adafruit_ADS1X15` або `RobTillaart/ADS1X15`, `OneWire` + `DallasTemperature`, `U8g2`, `ESPAsyncWebServer` або вбудований `WebServer`, `ArduinoJson`, `ESPmDNS`, `Update`.

## Безпечний старт

Порядок у `setup()` — саме такий:

1. Усі керуючі виходи (`SW1_ON`, `SW2_ON`, `K1`, `K2`) — `digitalWrite(LOW)` **до** `pinMode(OUTPUT)`; `SENS_PWR` — HIGH (датчики вимкнені). Апаратно все й так у OFF (Hi-Z + підтяжки), це лише підтвердження.
2. Watchdog задачі (10 с) і апаратний (30 с).
3. NVS: конфіг, лічильники, калібрування, збережений стан ключів і `sink`.
4. UART2, I2C, ADS1115 (перевірка присутності), OLED, 1-Wire (перелік адрес DS18B20).
5. `SENS_PWR` ← LOW (датчики живляться), 100 мс, перший блок відліків.
6. DPS: читання блоку; якщо `ONOFF = 1` — негайно `ONOFF ← 0` (DPS міг лишитися ввімкненим після нашого ресету).
7. Відновлення стану ключів **з NVS**, якщо з моменту збереження минуло < 60 с (uptime із RTC-пам'яті ресету) — інакше обидва OFF. Заряд після ресету **не відновлюється** автоматично, стан → IDLE, подія `boot` з `restored`.
8. Wi-Fi (STA; якщо немає конфігу або 60 с без зв'язку — AP `batman-<id>` зі сторінкою налаштування), mDNS, HTTP-сервер, UDP-слухач.
9. Основний цикл.

Ресет не змінює стану ключів (перевірка в 4.1 плану).

## Задачі й пріоритети

| Задача | Період | Що |
|---|---|---|
| `acq` (ядро 1, високий пріоритет) | за готовністю ADS1115 (~470 Гц) | відлік → інтегрування → буфер середніх |
| `ctrl` (ядро 1) | 500 мс | Modbus-опитування, стейт-машина, перехресні перевірки, ключі |
| `slow` (ядро 0) | 1 с | DS18B20, ADC1 (U_LOAD, I_LOAD), OLED, кнопка, NVS за розкладом |
| `net` (ядро 0) | за подіями | HTTP-сервер, телеметрія на sink, буфер, mDNS/UDP, OTA |
| ISR `FAULT` | — | ставить прапорець; `ctrl` реагує в наступному тику ≤ 500 мс, а самі виходи SW_ON/K скидаються **прямо в ISR** (`digitalWrite` безпечний) |

Доступ до спільних даних — через один м'ютекс на «знімок стану»; `acq` пише в подвійний буфер.

## Стейт-машина

Стани верхнього рівня:

| Стан | Що відбувається | DPS | K1/K2 |
|---|---|---|---|
| `IDLE` | нічого не заряджається; ключі за командами/порогами | OFF | розімкнені |
| `CHG_B1_CC` / `CHG_B2_BULK` | постійний струм `i_cc` / `i_bulk` | ON, I-SET = профіль, U-SET підтягується за U_BX | KX замкнене |
| `CHG_B1_CV` / `CHG_B2_ABS` | утримання `u_cv` / `u_abs` на вузлі B; струм падає | ON | KX |
| `CHG_B2_FLOAT` | свинець: `u_float` з термокомпенсацією; без обмеження часу | ON | K2 |
| `REST` | пауза між зарядами (`policy.rest_min`) | OFF | розімкнені |
| `NO_INPUT` | БЖ відсутній (UIN < 30 В) | — | розімкнені |
| `FAULT` | аварія; підстан у `fault.code` | OFF | розімкнені |

Переходи:

| З | У | Умова |
|---|---|---|
| IDLE | CHG_Bx_* | команда `charge_start`, або `policy.auto` і гілка x — з найнижчим SoC (або за `charge_order`) і не в REST; **і** T_x у межах (`t_min`…`t_max`), **і** DPS ok, **і** UIN ≥ 31 В |
| CHG_B1_CC | CHG_B1_CV | U_B1 ≥ `u_cv` − 0,05 В (з ADS1115, середнє 2 с) |
| CHG_B1_CV | IDLE (`tail_current`) | I_B1 ≤ `i_tail` протягом 60 с → «100 %» (measurement.md), подія `cycle_complete` |
| CHG_B2_BULK | CHG_B2_ABS | U_B2 ≥ `u_abs_tc` − 0,05 В |
| CHG_B2_ABS | CHG_B2_FLOAT | I_B2 ≤ `i_abs_end` протягом 60 с, **або** 4 год у ABS (`timeout`) → «100 %» |
| CHG_B2_FLOAT | IDLE | команда, або інша гілка потребує заряду (`policy`), або 24 год |
| будь-який CHG | IDLE | команда `charge_stop`; T поза межами (`t_low` / `T_OVER` → FAULT, якщо > `t_max` + 5) |
| будь-який | NO_INPUT | UIN < 30 В або DPS не відповідає на UIN 3 рази |
| NO_INPUT | IDLE | UIN ≥ 31 В стабільно 10 с і DPS ok |
| будь-який | FAULT | FAULT-засувка; PROTECT ≠ 0; DPS таймаут 3×; невідповідність стану DPS; `RELAY_STUCK` (струм у гілці при розімкненому K і вимкненому SW понад 0,3 А… при цьому SW не `forced`) |
| FAULT | IDLE | лише команда `fault_clear`, і лише якщо причина зникла |
| IDLE | REST | після завершення заряду, на `rest_min` хв |

Правила поверх таблиці:
- **Реле рухаються тільки при IOUT = 0 і ONOFF = 0** (dps5015-modbus.md). Ключі mSW — будь-коли.
- **Термокомпенсація свинцю:** `u_abs_tc = u_abs + tc × (T2 − t_ref)`, те саме для `u_float`; T2 відсутній → компенсація 0 і попередження `t_missing`.
- **LiFePO₄ нижче `t_min` (0 °C)** — заряд не стартує; якщо стартував і T1 впала — стоп (`t_low`).
- **Уставка за вузлом B:** U-SET підтягується так, щоб U_BX (ADS1115) = ціль; крок ≤ 0,05 В за 2 с; U-SET ніколи > `limits.u_set_max`; I-SET ніколи > `limits.i_set_max`.
- **Ключі розряду** (mSW): вручну (`switch`) і за порогами: `u_off` → OFF з подією `u_low`; назад — лише вручну або при `u_on` після заряду. Стан `forced` (повзунок ON) прошивка лише показує.
- **Заряд відрізаної гілки:** дозволено — це основний режим (заряджаємо ту, що не на навантаженні). Заряд гілки з увімкненим ключем теж дозволений (тоді частина струму йде в навантаження — облік чесний, бо датчик стоїть до розгалуження).

## FAULT і попередження

Коди — protocol.md. У FAULT: обидва SW_ON ← 0 (крім `forced`, там фізично не можемо), K ← 0, DPS ONOFF ← 0, OLED показує код великим шрифтом, подія в сервіс. `OC_LATCH` додатково: `SENS_PWR` HIGH 100 мс → LOW (скидання засувки) лише після `fault_clear`. Попередження не змінюють стан — лише масив `warn` у телеметрії й подія при появі/зникненні.

## OLED і кнопка

Екрани (кнопка — наступний; утримання 2 с — назад на перший): 1) стан + U/I обох гілок + SoC; 2) заряд: стан, U-SET/I-SET, UOUT/IOUT, час у стані; 3) лічильники циклу й загальні; 4) температури, U_LOAD/I_LOAD; 5) Wi-Fi: SSID, IP, RSSI, sink, буфер; 6) FAULT/warn — лише коли є. Гасіння за `oled.timeout_s`, будь-яке натискання будить; кожні 10 хв зсув картинки на 1 px по колу (випалювання). Утримання 5 с на екрані 1 — `charge_stop` + обидва ключі OFF (аварійна кнопка без телефона).

## Wi-Fi, телеметрія, OTA

- STA з реконектом (експоненційно 1…60 с); без конфігу — AP + captive-сторінка (SSID, пароль, IP сервісу опційно).
- mDNS + UDP-відповідач (protocol.md); HTTP на 80.
- Телеметрія — окрема задача, не блокує `ctrl`; таймаут POST 3 с; буфер за protocol.md.
- OTA через `POST /update` (перевірка розміру й magic-байта, `Update.end(true)`), а також ArduinoOTA у локальній мережі для розробки. Під час OTA стейт-машина в поточному стані заморожується, DPS не чіпаємо; після ресету — безпечний старт.
- Час: NTP лише для OLED/журналу.

## Журнал і діагностика

UART0 115200: рівні `E/W/I/D`, теги за задачами; `GET /status` віддає `heap`, `min_heap`, `uptime`, `reset_reason`, лічильники CRC-помилок Modbus, втрат телеметрії, переповнень буфера. Раз на годину — рядок `I` з усіма лічильниками (для кроку 4.8 плану: тиждень без витоку heap).

## Версія і збірка

`fw` — semver у `version.h`, автоінкремент build-номера скриптом PlatformIO; у телеметрії та mDNS TXT. `platformio.ini`: `board = esp32dev`, `monitor_speed = 115200`, розділ прошивки з OTA (`partitions = min_spiffs.csv` або `default.csv`).
